Problem

The inventory import endpoint works for small files, but a customer uploaded a CSV with tens of thousands of rows and the service's memory usage spiked. The current path appears to read the entire upload into memory before parsing it. The endpoint should handle larger files without holding a second full copy in memory, while preserving its current response format and all-or-nothing database behavior.

The endpoint accepts a CSV containing these columns: sku, warehouse, quantity, and updated_at. A row identifies one inventory count for a stock keeping unit at a warehouse. Quantity must be a nonnegative whole number. SKU and warehouse are required strings; updated_at is an ISO 8601 timestamp. The route currently authenticates callers and checks that the caller can update the requested warehouse. Keep those checks in place. Existing clients rely on the current URL, HTTP method, success status, and JSON response fields, so do not change the public API unless the repository makes that unavoidable.

Please inspect the existing code before choosing how to stream the upload. Account for UTF-8 input, an optional UTF-8 byte order mark, standard CSV quoting, commas inside quoted fields, quoted fields containing line breaks, CRLF line endings, and blank rows. Do not split rows by commas or newlines manually. Report validation errors with the physical CSV line number and a useful description, without including the full contents of a potentially sensitive row. Reject missing or duplicate required headers, malformed CSV, invalid timestamps, negative or fractional quantities, and rows whose warehouse does not match the authorized warehouse. If there are established limits for request size or row count, follow them; otherwise add a conservative limit and document it near the existing validation logic.

The import must remain atomic. If parsing or validation fails late in the file, none of the earlier rows may have been committed. If the repository already stages imports or uses a database transaction for this route, preserve that behavior. Avoid building an unbounded list of parsed rows before writing them. Use the project's existing database and async patterns rather than adding a new framework or dependency. Keep duplicate-row behavior consistent with the existing endpoint and tests; if it is not defined, add a clear test and use the least surprising behavior supported by the current schema.

Add or update focused tests for a valid multi-row import, a quoted field containing a comma, a quoted field containing a newline, a UTF-8 BOM, malformed CSV, a validation error after at least one valid row, and preservation of atomicity when that late error occurs. Include a test for whatever size or row-count limit you enforce. Reuse existing test helpers and fixtures. Do not make unrelated formatting or naming changes.
